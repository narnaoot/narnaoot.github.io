Reducing Crashes for iTunes

Business Analysis Tableau Apple

Started with an incomprehensible spreadsheet. Ended with real changes that improved iTunes stability — and let on-call engineers sleep through the night.

01
Prototype
Build something — anything — that works.
Create a MySQL database and Tableau report. Load new data manually every week.
02
Scale
Stop doing it by hand.
Find the company-wide database system. Modify it to add the data I need.
03
Process
Give crashes a proper home.
Build a process for iTunes crashes that includes recording the cause. Train the team. Convince everybody to use it.
04
Automate
Make it run itself.
Lead the web development team in creating a web-based system to handle everything automatically.
05
Analyze
The data finally speaks.
Discover and present data showing that the main reason iTunes crashes is because of old software bugs.
06
Change
The VP acts. The pagers go quiet.
The iTunes VP assigns developers to fix old bugs. iTunes stabilizes. On-call teammates sleep through the night.
This is my favorite kind of project: one where cleaning up a mess creates something genuinely useful — and where teammates stop getting woken up at 3am.

Bringing Clarity to ML: Explainability with SHAP

ML Python Data Science

A tutorial on using SHAP to make machine learning models understandable — to humans. Because as more and more life-changing decisions get made by models designed to be incomprehensible, we absolutely must do a better job explaining how they work.

Covers Shapley values from first principles, then walks through linear regression examples, partial dependence plots, waterfall plots, and bar charts showing average variable importance — with explicit attention to assumptions and edge cases.

If a model affects someone's mortgage, job application, or medical diagnosis, "it's complicated" is not a good enough answer.

Conditional Probability for Normal Humans

Statistics Writing

If you test positive for malaria, how likely is it that you actually have malaria? Many doctors don't even understand the answer. This piece explains it — without complicated formulas — because important ideas shouldn't require a statistics degree to access.

Making something genuinely understandable is harder than making it technically correct. I think about that a lot.

Method

The questions I always ask.

Before I build anything, I ask questions. These six have never failed me. They're split into two phases: opening the conversation, and figuring out what's actually wrong.

Phase 1 — Opening
1
"It's six months from now. You are really happy. What has changed?"
This tells you what actually matters.
2
"What is keeping you from getting your work done?"
Not what you want to build — what's in the way.
3
"What terrible, manual task do you absolutely hate doing?"
Where automation and process redesign live.
Phase 2 — Diagnosis
4
"What's getting in your way?"
The friction around work: dependencies, approvals, handoffs.
5
"What do you need to know to fix that?"
Understanding the information gap.
6
"What does the team already know that executives need to be convinced of?"
Making problems legible upward. A translation job.
